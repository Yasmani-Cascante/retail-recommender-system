Cold Start UX — 3 Enfoques

¿Cómo detecta el frontend que el servicio está dormido?

A

SSE — Push en tiempo real

El widget mantiene una conexión Server-Sent Events abierta mientras el chat está activo. Durante el SHUTDOWN, el backend empuja un evento service_shutdown al frontend al instante.

✓ Pros

  • Notificación instantánea (0s lag)
  • Fiel a "backend envía señal"
  • Reutilizable para futuros eventos

✗ Cons

  • Nueva infraestructura SSE en FastAPI
  • Conexión persistente por cada chat abierto
  • Mayor complejidad en Cloud Run (timeouts)

⏱ Detección: <1s · Complejidad: Alta

B

Redis Flag + Polling liviano ⭐ Recomendado

SHUTDOWN escribe service:shutdown_at en Redis. El widget, cuando hasUserMessages === true, hace un poll cada 30s a /v1/health/status. Si el flag existe o la request falla → muestra el UI inline.

✓ Pros

  • Sin nueva infraestructura de conexión
  • Backend ya tiene Redis — solo escribir un key
  • 30s lag es aceptable (shutdown tarda minutos)
  • Funciona incluso si SSE falla

✗ Cons

  • Polling cada 30s mientras chat abierto
  • Hasta 30s de lag post-shutdown

⏱ Detección: <30s · Complejidad: Baja

C

Híbrido: Timer frontend + Fallo reactivo

El frontend gestiona todo: timer de inactividad de 15 min → "¿Sigues ahí?" (preventivo). A los 20 min o si el mensaje falla con 503 → muestra los 3 botones. Sin comunicación backend extra.

✓ Pros

  • Cero overhead de red adicional
  • Implementación más simple (solo frontend)
  • Patrón idéntico al de Zalando

✗ Cons

  • No hay señal real del backend
  • El timer (20min) puede no coincidir con el timeout real de Cloud Run
  • Caso reactivo: el usuario ya intentó enviar un mensaje

⏱ Detección: basada en timer · Complejidad: Muy baja

💡 En los 3 enfoques se mantiene:
  • Timer preventivo 15min → "¿Sigues ahí?" (como Zalando)
  • Cold start detection al abrir el chat (case 1)
  • "Let's continue" → recap C-lite desde Redis (últimos 2 turnos)
