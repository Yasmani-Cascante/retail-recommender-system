# **1\. Overview**

This document is the authoritative technical reference for the conversational AI system embedded in the Retail Recommender platform. It describes the architecture of the chat widget, the backend processing pipeline, the intent detection engine, and the decisions made during the implementation phases leading up to production readiness in March 2026.

## **1.1 System Description**

The Retail Recommender Conversational System is an AI-powered chat assistant for e-commerce. It is deployed as a lightweight embeddable widget on Shopify storefronts (and any HTML page) and communicates with a FastAPI backend hosted on Google Cloud Run. The system serves two categories of user requests:

-   Informational queries — questions about store policies (returns, shipping, payments, warranties, sizing), answered from a Knowledge Base synchronised from Shopify CMS via metafields.
-   Transactional queries — product discovery requests, answered with personalised recommendations generated by the Hybrid Recommender + MCP Personalisation Engine pipeline.

## **1.2 Business Context**

The platform targets fashion e-commerce retailers operating across multiple markets (ES, US, MX, CL). Shoppers interact with the chat widget to resolve purchase doubts without leaving the storefront, replacing the need for human support for common queries. Product recommendations surface relevant inventory in a conversational format, increasing product discovery and conversion.

| **Dimension** | **Description** |
| --- | --- |
| Primary market | Spain (ES) — Euro currency, Spanish language |
| Additional markets | US, Mexico (MX), Chile (CL) |
| Platform | Shopify Storefront + Any HTML page |
| AI model | Claude 3 Haiku (Anthropic) — conversational personalisation |
| Languages | Spanish (es), English (en) — auto-detected |
| Deployment | Google Cloud Run (us-central1), min-instances=0 |

# **2\. System Architecture**

## **2.1 High-Level Architecture**

The system follows a three-tier architecture: the embeddable frontend widget, the FastAPI backend on Cloud Run, and a set of external integrations.

| **Tier** | **Component** | **Technology** | **Hosting** |
| --- | --- | --- | --- |
| Frontend | Chat Widget | React 18 + TypeScript + Vite (UMD bundle) | Shopify / CDN via Cloud Run |
| Backend | API Gateway | FastAPI 0.115 + Uvicorn | Google Cloud Run (us-central1) |
| Backend | Intent Detection | Rule-based + sklearn TF-IDF + LR (hybrid) | In-process (Cloud Run) |
| Backend | MCP Conversation Engine | Claude 3 Haiku via Anthropic API | External API |
| Backend | Recommender | TF-IDF HybridRecommender + MCPPersonalisationEngine | In-process |
| Data | Knowledge Base | PostgreSQL (Neon) + Redis + Shopify Metafields | Neon Serverless / Redis Cloud |
| Data | Session State | Redis (TTL 86400 s) | Redis Cloud |

## **2.2 Frontend Architecture**

### **2.2.1 Widget Structure**

The widget is compiled as a single UMD bundle (widget.umd.cjs, ~150 KB) that includes all JavaScript and CSS. CSS is injected at runtime into the host page's <head> via vite-plugin-css-injected-by-js, eliminating the need for a separate stylesheet and resolving the Shopify loading issue present in earlier builds.

| src/frontend/   ├── src/   │ ├── main.tsx ← Entry: window.RetailRecommenderWidget API   │ ├── services/api.ts ← ConversationAPI (session, identity, HTTP)   │ ├── components/   │ │ ├── ChatWidget.tsx ← Root: full panel + conversation state   │ │ ├── ChatBubble.tsx ← Floating trigger button (position: fixed)   │ │ ├── MessageList.tsx ← Message rendering + typing indicator   │ │ ├── MessageInput.tsx ← Text input (auto-expanding textarea)   │ │ └── ProductCard.tsx ← Product recommendation card   │ └── styles/main.css ← Global keyframe animations only   └── static/widget/   ├── widget.umd.cjs ← Production bundle (JS + inline CSS)   └── embed.js ← Shopify initialisation loader |
| --- |

### **2.2.2 Session and Identity Management**

Identity is managed in two layers. The user identity (userId) is persisted in localStorage under the key rr\_widget\_user\_id and survives browser sessions. The conversation session (sessionId) is generated per widget instantiation with the format widget\_session\_{timestamp}\_{random} and is synchronised with the backend session\_id after the first successful message exchange.

| **Concern** | **Mechanism** |
| --- | --- |
| User identity | localStorage key rr_widget_user_id (survives sessions) |
| Session identity | widget_session_{ts}_{rand} → synced with backend session_id |
| Session TTL | 86,400 s (Redis) — persists full conversation history across page reloads |
| Language | navigator.language (first 2 chars) sent in Accept-Language header |
| Market | Injected via data-market-id attribute on the &lt;script&gt; tag |
| Page context | page_url, page_type, product_id extracted from URL/meta tags and sent in widget_context |

## **2.3 Backend Architecture**

### **2.3.1 Primary Endpoint**

All conversational interactions flow through a single endpoint:

| POST /v1/mcp/conversation   Content-Type: application/json   X-API-Key: {key}   Accept-Language: {navigator.language} |
| --- |

The endpoint is protected by API key authentication and returns a ConversationResponse Pydantic model. Fields include: answer (primary text for the chat bubble), kb\_document (full Knowledge Base source document for informational responses), recommendations (list of product cards), session\_metadata, intent\_analysis, market\_context, and personalization\_metadata.

### **2.3.2 Request Processing Flow**

Each request follows a sequential pipeline within get\_mcp\_conversation\_recommendations():

| Phase 1 → Load or create MCP conversation context (Redis session)   Phase 1.5→ Intent Detection (ENABLE\_INTENT\_DETECTION=true)   ├─ GREETING → template response, no products, early return   ├─ INFORMATIONAL (confidence ≥ 0.7)   │ ├─ KB lookup (Redis → PostgreSQL → Shopify GraphQL)   │ ├─ has\_specific\_entities() → contextualise with Claude Haiku   │ └─ early return: {answer, kb\_document, recommendations: \[\]}   └─ TRANSACTIONAL → continue to Phase 2   Phase 2 → Parallel execution:   ├─ HybridRecommender.get\_recommendations() \[w/ diversification\]   ├─ MCPPersonalisationEngine preparation (warm singleton)   └─ MarketAdapter preparation   Phase 3 → MCPPersonalisationEngine.generate\_personalized\_response()   (Claude Haiku call, timeout 12 s, personalisation cache 5 min)   Phase 4 → MarketAdapter.adapt\_product() per recommendation   Phase 5 → State persistence (Redis), response serialisation |
| --- |

# **3\. Conversational System Design**

## **3.1 Complete Interaction Flow**

The following describes the lifecycle of a user interaction from widget open to rendered response:

| \[1\] User opens widget   → ChatWidget mounts, welcome message rendered locally (no API call)   → sessionId generated, userId loaded from localStorage      \[2\] User types and submits message   → Message{type:'user'} added to UI state immediately (optimistic update)   → isLoading: true → typing indicator (three animated dots)   → ConversationAPI.sendMessage(text) POST to /v1/mcp/conversation      \[3\] Backend: Intent Detection (Phase 1.5)   → RuleBasedIntentDetector.detect(query)   → if ML enabled: HybridIntentDetector (rule-based + sklearn fallback)   → Result: IntentType.GREETING \| INFORMATIONAL \| TRANSACTIONAL      \[4a\] INFORMATIONAL path   → kb.get\_answer(sub\_intent, language) ← triple-layer cache   → has\_specific\_entities()? → generate\_contextual\_answer() via Haiku   → Response: {answer: str, kb\_document: str, recommendations: \[\]}   → Router early-return (skips personalisation pipeline)      \[4b\] TRANSACTIONAL path   → HybridRecommender.get\_recommendations(query, user\_id, n=5)   → MCPPersonalisationEngine.generate\_personalized\_response()   → MarketAdapter.adapt\_product() per item   → Response: {answer: str, recommendations: \[{id, title, price, score}\]}      \[5\] Frontend renders response   → Message{type:'assistant', content: answer} added to MessageList   → ProductCard\[\] rendered below message text if recommendations present   → Informational: answer shown; kb\_document available for "view full policy"   → isLoading: false, input re-enabled |
| --- |

## **3.2 Intent Detection Engine**

### **3.2.1 Architecture: Hybrid Detector**

The intent detection system uses a two-layer hybrid architecture. Rule-based detection runs first (sub-millisecond, deterministic). If the rule-based confidence falls below the configured threshold (default 0.7), the ML classifier is invoked as a fallback. If the ML model fails or is disabled, the system defaults to TRANSACTIONAL (safe degradation — products are always a valid response).

| **Layer** | **Implementation** | **Latency** | **When active** |
| --- | --- | --- | --- |
| Rule-based (primary) | RuleBasedIntentDetector — regex scoring | &lt; 1 ms | Always |
| ML fallback | sklearn TF-IDF + Logistic Regression | 0.16 ms avg | ML_INTENT_ENABLED=true |
| Default fallback | TRANSACTIONAL with confidence 0.5 | 0 ms | No match found |

### **3.2.2 Rule-Based Detector Scoring**

The rule-based detector uses a weighted scoring system. Each matched keyword contributes +0.4 points. The first matching question\_word contributes a one-time +0.3 bonus. A negative\_context match adds a further +0.2 bonus. The minimum score to classify as INFORMATIONAL is 0.7. Scores are capped at 1.0.

| **Signal type** | **Score contribution** |
| --- | --- |
| Keyword match | +0.4 per keyword matched (additive) |
| Question word match | +0.3 one-time bonus (first match only) |
| Negative context | +0.2 one-time bonus (first match only) |
| INFORMATIONAL threshold | ≥ 0.70 |
| TRANSACTIONAL threshold | ≥ 0.50 |
| Default (no match) | TRANSACTIONAL, confidence 0.50 |

### **3.2.3 Intent Types and Sub-Intents**

Three primary intent types are detected. GREETING and INFORMATIONAL trigger early-return paths that bypass the recommendation engine entirely. TRANSACTIONAL continues to the full product personalisation pipeline.

| **Intent** | **Sub-Intents** | **Response type** |
| --- | --- | --- |
| GREETING | — (none) | Bilingual template, no API call to Claude |
| INFORMATIONAL | policy_return, policy_shipping, policy_payment, policy_warranty, policy_privacy, product_material, product_sizing, product_care, product_availability, account_orders, account_modifications, general_faq | KB document ± Claude contextualisation |
| TRANSACTIONAL | product_search, product_view, purchase_intent | Personalised product recommendations |

### **3.2.4 ML Classifier**

The ML classifier (MLIntentClassifier) uses a TF-IDF vectoriser (vocabulary size 3,000, n-gram range 1–2) followed by a Logistic Regression model trained on a synthetic dataset of 4,944 queries generated with Claude. The model achieves 96.25% accuracy on the test set and 97.27% cross-validation accuracy. Inference latency averages 0.16 ms with a throughput of 1,315 queries per second.

| **Metric** | **Value** |
| --- | --- |
| Training samples | 4,944 (50/50 INFORMATIONAL/TRANSACTIONAL) |
| Test accuracy | 96.25 % |
| CV accuracy (5-fold) | 97.27 % ± 0.36 % |
| Inference latency | 0.16 ms average, 1.0 ms P95/P99 |
| Throughput | 1,315 queries/sec |
| Model size | model.pkl 24 KB + vectorizer.pkl 107 KB |
| sklearn version | 1.6.1 (must match training environment) |

### **3.2.5 KB Contextualisation (has\_specific\_entities)**

When a query is classified as INFORMATIONAL, the system checks whether it contains named entities that exceed the sub-intent label — specific card brands, carriers, measurement values, etc. This check (kb\_contextualizer.py) runs in under 1 ms using pre-compiled regex. If specific entities are found, a Claude Haiku call is made to generate a focused 2–3 sentence answer using the KB document as context (RAG pattern, max\_tokens=250, temperature=0.3, timeout=3.0 s). If the call fails or times out, the full KB document is returned verbatim.

| Example:   Query: "¿Puedo pagar con mi tarjeta Visa?"   sub\_intent: policy\_payment   has\_specific\_entities() → True ("Visa" matches card brand pattern)   → generate\_contextual\_answer(query, kb\_document, sub\_intent)   → answer: "Sí, puede pagar con su tarjeta Visa. El documento indica   que aceptamos tarjetas Visa como uno de los métodos de pago."   → kb\_document: <full payment policy text>      Query: "¿Cuáles son los métodos de pago aceptados?"   has\_specific\_entities() → False (no specific brand/method named)   → answer = kb\_document (returned verbatim) |
| --- |

## **4.2 Error Handling and Timeouts**

Error handling is layered across the frontend and backend. The frontend classifies errors by HTTP prefix to provide user-appropriate messages without exposing internal details. The backend has multiple fallback layers to ensure a response is always returned.

| **Error condition** | **Frontend message** | **Backend behaviour** |
| --- | --- | --- |
| HTTP 401/403 | Authentication error | API key validation failed |
| HTTP 429 | Too many requests, try later | Rate limit enforced |
| HTTP 5xx | Server error, try again | Emergency response dict returned |
| Network failure (fetch) | Connection error — check network | N/A |
| Claude API timeout (12 s) | Generic response returned | Base recommendations used without personalisation |
| KB lookup failure | Products shown instead | Falls through to TRANSACTIONAL path |
| ML model not fitted | Rule-based detection used | HybridDetector degrades gracefully |

## **5.3 MCP Conversation Handler**

The central backend orchestrator (mcp\_conversation\_handler.py) implements the multi-phase pipeline described in Section 2.3.2. It manages conversation context loading from Redis, intent detection gating, parallel execution of base recommendation fetching and engine preparation, personalisation cache checks, Claude Haiku calls, market adaptation, and state persistence.

## **5.4 Knowledge Base System**

The Knowledge Base uses a three-layer cache strategy to minimise latency while keeping content current with Shopify CMS:

-   Layer 1 — Redis: sub-millisecond reads, TTL-controlled invalidation.
-   Layer 2 — PostgreSQL (Neon): structured storage of KB entries synchronised from Shopify, queried on Redis miss.
-   Layer 3 — Shopify GraphQL: source of truth for KB content, queried on PostgreSQL miss or forced refresh.

KB entries are keyed by (sub\_intent, language, market\_id). The system supports bilingual content (es/en) and falls back from Spanish to English when a translation is missing.

## **5.5 Recommendation Engine**

The recommendation engine is a hybrid system combining TF-IDF content-based filtering (HybridRecommender) for base retrieval with MCPPersonalisationEngine (Claude Haiku) for conversational personalisation. Recommendation diversification is applied from the second turn onwards: products already shown in previous turns are excluded using session-stored recommendation IDs.

# **7\. Solutions Implemented**

## **P-01 — ResponseValidationError HTTP 500**

### **Problem**

The recommendation handler returned Pydantic model instances and custom objects in the recommendations list. FastAPI's Pydantic v2 serialiser expects List\[Dict\[str, Any\]\] and raises a ResponseValidationError on any non-dict element.

### **Solution**

Added a sanitisation cascade before the router return: isinstance(dict) → model\_dump() → vars() → dict(). Applied in mcp\_router.py before all return paths.

### **Trade-offs**

Minimal overhead per request (single pass over 5–10 items). Alternative of changing the Pydantic type to List\[Any\] was rejected as it removes response contract guarantees.

## **P-02 — CSS not applied in Shopify**

### **Problem**

Vite in library mode (lib build) generates a separate style.css file that is never loaded by Shopify — only the UMD JavaScript bundle is injected by embed.js.

### **Solution**

Migrated all component styles from Tailwind utility classes to CSS Modules (scoped, hash-named). Added vite-plugin-css-injected-by-js to the Vite build config. The plugin converts all compiled CSS to a string literal and injects a <style> tag into document.head at bundle load time. No separate file required.

### **Trade-offs**

Bundle size increases by ~15 KB (CSS now inline). Acceptable given the single-file deployment requirement. The position: fixed stacking context issue was also resolved by ensuring the widget root container never uses position: relative.

## **P-03 — Intent detection block silently skipped**

### **Problem**

Three compounding issues: (1) a module-level import of hybrid\_detector crashed silently during cold start, preventing the entire handler module from loading correctly; (2) logger.debug calls were invisible with LOG\_LEVEL=INFO; (3) the ENABLE\_INTENT\_DETECTION environment variable was read via Pydantic settings with @lru\_cache, which froze the value at startup before Cloud Run injected environment variables — returning False even when the env var was set to true.

### **Solution**

(1) Moved the hybrid\_detector import to lazy (inside the ML-enabled block). (2) Promoted all diagnostic logs to logger.info. (3) Replaced Pydantic settings read with direct os.environ.get() for the ENABLE\_INTENT\_DETECTION and ML\_INTENT\_ENABLED flags — these are the only two flags affected by the lru\_cache startup freeze.

### **Trade-offs**

Direct os.environ.get() bypasses Pydantic's type validation for these two flags. Acceptable given they are boolean flags read as strings ('true'/'false'). All other settings continue to use the typed Pydantic Settings class.

## **P-04 — Greetings returned product lists**

### **Problem**

Greetings like 'Hi!' and 'Hola!' are not questions (no question mark, no question word), so the is\_question() gate excluded them from the INFORMATIONAL detection path. They fell through to the TRANSACTIONAL default with confidence 0.5, triggering a full product recommendation call with no greeting text.

### **Solution**

Added a GREETING detection step (Step 0) in the RuleBasedIntentDetector.detect() method, executed before the is\_question() check. GREETING returns confidence 0.95 with an early return, bypassing all subsequent intent detection logic. The handler has a dedicated GREETING branch that returns a bilingual template response without any Claude or recommender call.

### **Trade-offs**

Template response has no personalisation. Accepted trade-off: greeting responses should be brief and immediate; personalised greetings would add 200–800 ms latency for no meaningful value.

## **P-05 / P-06 — Payment and shipping intent scoring below threshold**

### **Problem**

"Cuáles son los métodos de pago aceptados?" scored only 0.4 (one keyword: pagos) because the pattern for POLICY\_PAYMENT did not include métodos as a keyword, and the question\_word pattern for aceptan did not cover the morphological variant aceptados. "hacen envios hasta casa?" scored 0.0 because \\b(envio)\\b requires a word boundary after 'o', which does not exist before 's' in envios (trailing character is alphabetic).

### **Solution**

(P-05) Added métodos/metodos/method/methods as keywords in POLICY\_PAYMENT; broadened the aceptan question\_word regex to acepta(n|dos?)? to cover all verb forms; added cuáles/son/are/what as question\_words. (P-06) Changed the shipping keyword regex to envíos?|envios?|envía(n|s)?|envia(n|s)?|shipping|deliver(y|s)?|entregas?; added domicilio, a casa, home delivery as explicit keywords; added hacen/mandan/llega/dirección/home to question\_words.

### **Trade-offs**

Adding métodos as a keyword increases the risk of false positives if used alone. This is mitigated by requiring at least one other payment keyword (pago, pagar, tarjeta, etc.) for the score to reach 0.7. Tested against 13 query variants with 100% pass rate.

## **P-07 — Prior turn query used in personalisation engine**

### **Problem**

MCPPersonalisationEngine.\_determine\_optimal\_strategy() reads the current query from mcp\_context.turns\[-1\].user\_query. Since the router persists the current turn after the handler returns, turns\[-1\] at handler execution time is the previous turn's query. On cache hits, mcp\_context.current\_query was never set, so the engine used the wrong query.

### **Solution**

Injected mcp\_context.current\_query = conversation\_query before the personalisation cache check (not inside the cache-miss branch). This ensures both the cache-hit path and cache-miss path operate on the correct current query.

## **P-08 — Raw JSON dict visible in chat bubble**

### **Problem**

For INFORMATIONAL and GREETING responses, the handler returns early with type='informational' or 'greeting'. Without a response\_type check in the router, execution fell through to the second personalisation path, which calls mcp\_recommender.generate\_personalized\_response(). This method returns a structured dict {response: '...', tone\_adaptation: ..., ...} that was converted to a string via str(dict) and displayed verbatim in the chat.

### **Solution**

Added an early-return guard in the router: if response\_type in ('informational', 'greeting'), persist the turn and return immediately without executing the personalisation path.

## **P-09 — kb\_document missing from API response**

### **Problem**

Two independent barriers: (1) the router's early-return dict did not include the kb\_document key extracted from response\_dict; (2) the ConversationResponse Pydantic model did not declare kb\_document as a field — Pydantic v2 silently drops undeclared keys.

### **Solution**

(1) Added kb\_document = response\_dict.get('kb\_document', '') before the return dict and included 'kb\_document': kb\_document in the return. (2) Added kb\_document: str = '' to the ConversationResponse Pydantic model.

## **P-10 — sklearn version mismatch**

### **Problem**

The intent classifier model (model.pkl, vectorizer.pkl) was trained with scikit-learn 1.6.1. The Cloud Run container used requirements.cloudrun.txt which pinned scikit-learn==1.2.2. joblib loads the pickle without error but the TfidfVectorizer internal attribute idf\_ is not correctly deserialised across major versions, resulting in NotFittedError on the first transform call.

### **Solution**

Updated requirements.cloudrun.txt to scikit-learn==1.6.1. Verified numpy==1.23.5 and scipy==1.10.1 are compatible with sklearn 1.6.1 (minimum requirements: numpy>=1.19.5, scipy>=1.3.2 — both satisfied).

### **Prevention**

Going forward, metadata.json should record the sklearn\_version used during training. The MLIntentClassifier.load() method should emit a warning when trained\_sklearn\_version != current\_sklearn\_version.

# **8\. Current Limitations and Gaps**

## **8.1 Conversational System**

| **Limitation** | **Description** | **Severity** |
| --- | --- | --- |
| No true multi-turn memory | Each request loads session state from Redis but the Claude prompt does not include full conversation history. Contextual follow-ups ("the second one" referring to a prior recommendation) are not understood. | Medium |
| Single KB document per sub-intent | Each sub-intent maps to one KB document. Two questions with the same sub-intent receive the same source document. Claude contextualisation partially mitigates this for specific entity queries. | Medium |
| Rule-based intent coverage gaps | Natural language variants not covered by regex patterns fall to TRANSACTIONAL. Each gap requires a code change and deploy to fix. | Medium |
| Cold start latency | Cloud Run min-instances=0 causes ~3–5 s cold start penalty on first request after idle. Keep-alive ping (Haiku, every 90 s) is in place but not always sufficient to prevent cold starts. | Medium |
| Personalisation cache collision | The diversity_cache_v2 was observed caching by user_id without including the query hash, returning stale personalised results for different queries from the same user within the 5-minute TTL. | Low-Medium |

## **8.2 Frontend / UX**

| **Item** | **Status** | **Impact** |
| --- | --- | --- |
| Product URL navigation | ProductCard has no link to the product page (url field not reliably returned) | User cannot navigate to product from recommendation |
| Currency display | ProductCard currency is partially hardcoded; ES market may show EUR correctly but MX/US require market-aware formatting | Price display may be incorrect for non-ES markets |
| Dark/auto theme | Only light theme is implemented; dark and auto are declared in WidgetConfig but have no effect | Cosmetic — no functional impact |
| No frontend test coverage | Zero unit or integration tests exist for React components | Regression risk on future changes |
| Shopify REST API deprecation | Translations require GraphQL API — REST was deprecated Oct 2024. Any remaining REST calls for translations will silently fail. | Content accuracy risk for translated markets |

## **8.3 External Dependencies**

-   Anthropic API latency: Claude Haiku calls average 300–700 ms for KB contextualisation and 1.2–7.5 s for full personalisation. The 12 s timeout provides headroom but responses are blocked during this window.
-   Shopify GraphQL rate limits: KB synchronisation is rate-limited. Bulk sync operations require pagination and backoff logic.
-   Neon serverless cold start: PostgreSQL connections via Neon may experience 200–500 ms connection overhead on cold starts.
-   Redis availability: If the Redis connection is lost, session state falls back to in-memory with no cross-instance persistence. Recommendation diversification is disabled in fallback mode.

# **9\. Design Decisions**

## **9.1 Hybrid Intent Detection: Rule-Based First, ML Fallback**

Decision: Use a rule-based detector as the primary classifier and invoke the ML model only when rule-based confidence falls below 0.7.

Rationale: Rule-based detection is deterministic, zero-latency, requires no infrastructure, and is trivially debuggable — matching patterns can be inspected in plain Python. The ML model provides value for morphologically ambiguous queries that regex cannot cleanly handle (e.g. single-keyword queries, colloquial phrasing). The threshold (0.7) was chosen to maximise rule-based usage (estimated 50–70% of production queries) while allowing ML to rescue genuinely ambiguous cases.

Alternative considered: ML-only detection. Rejected because: (a) requires sklearn in the hot path for every request, (b) less interpretable for debugging production issues, (c) requires retraining to add new intent patterns.

## **9.2 Stateful Sessions with Redis, Stateless HTTP**

Decision: Each HTTP request is stateless (no server-side request affinity required). Conversation state is persisted in Redis keyed by session\_id with a 24-hour TTL.

Rationale: Cloud Run scales horizontally with min-instances=0. Any instance must be able to serve any request. Redis provides the shared state layer. The 24-hour TTL covers a typical shopping session including returns the next day.

Trade-off: Adds a Redis round-trip per request (~2–5 ms). Acceptable given overall response times of 200–800 ms for typical flows.

## **9.3 Early Return for Informational and Greeting Intents**

Decision: When the intent detector classifies a query as INFORMATIONAL or GREETING, the handler returns immediately after the KB lookup / template response, bypassing the entire recommendation pipeline (base retrieval, personalisation, market adaptation).

Rationale: These responses do not benefit from product recommendations. Executing the full pipeline would add 1–3 s latency for no user value. The early return path reduces median response time for KB queries to under 800 ms (vs. 2–4 s for full pipeline).

Trade-off: Future features that want to show "related products" below a KB response will require modifying the early-return path. Accepted as a deliberate architectural decision — product surfacing alongside KB answers is a product decision, not a default.

## **9.4 CSS Modules + vite-plugin-css-injected-by-js**

Decision: Use CSS Modules for component scoping and inject all CSS inline into the UMD bundle.

Rationale: The widget must work in any HTML host (Shopify, custom sites) without requiring the host to load a separate stylesheet. vite-plugin-css-injected-by-js is the standard solution for this in Vite library mode builds. CSS Modules prevent class name collisions with the host page styles.

Alternative considered: Shadow DOM encapsulation. Rejected because Shadow DOM introduces complexity around font inheritance, z-index stacking, and form submission events that are unnecessary for this widget's scope.

## **9.5 Single UMD Bundle with embed.js Loader**

Decision: The widget is distributed as two files: embed.js (the Shopify <script> tag target) and widget.umd.cjs (the full React application bundle). embed.js dynamically loads widget.umd.cjs.

Rationale: The double-load pattern decouples the Shopify theme snippet (which changes rarely) from the widget bundle (which deploys frequently). Updating the widget requires only a Cloud Run deploy; no Shopify theme editor access is needed.

# **10\. Future Evolution**

## **10.1 Conversational Memory (Context-Aware Responses)**

The highest-impact improvement is including the conversation history in the Claude prompt for personalisation calls. This would enable follow-up understanding ("the third one", "something cheaper") and preference tracking across turns within a session. Implementation requires: (1) serialising the last N turns from Redis into the Haiku prompt; (2) extending the MCPConversationContext data model to store compressed summaries for long sessions; (3) updating the knowledge base contextualisation prompt to reference prior exchange context.

Estimated complexity: Medium. Risk: token cost increase per request (~2× for 3-turn history). Mitigation: limit history inclusion to last 3 turns.

## **10.2 Intent Detection: Continuous Learning**

The ML classifier was trained on a synthetic dataset. As production query data accumulates, retraining with real query/intent pairs will improve accuracy for domain-specific phrasing. Recommended at 1,000+ real classified queries. The architecture supports this with no structural changes — only model.pkl and vectorizer.pkl need replacing.

## **10.3 Advanced Personalisation**

Current personalisation is session-scoped (within a single browser session). Persistent user profiles (cross-session preference learning) would require: (1) a PostgreSQL user preferences table; (2) periodic profile update jobs triggered by session close; (3) profile injection into the MCP context at session start. This is a medium-complexity addition fully supported by the existing MCPConversationContext model.

## **10.4 Latency Optimisation**

-   min-instances=1: Eliminates cold starts at a cost of ~$20–30/month. Recommended once traffic exceeds 100 sessions/day.
-   Pre-rendered welcome message: Frontend pre-fetches the first assistant message on widget open (before the user types) to reduce perceived response latency on first interaction.
-   Streaming responses: The Anthropic API supports SSR streaming. Implementing streaming in the widget would allow the first tokens to render in ~200 ms instead of waiting for the full response.
-   KB response caching: Cache KB answers by (sub\_intent, language, market\_id) in Redis with a TTL aligned to the KB sync schedule, eliminating PostgreSQL lookups for common informational queries.

## **10.5 Frontend Completeness**

-   Product URL navigation: Backend to reliably return url in the recommendation payload; ProductCard to open the product page in a new tab.
-   Dark / auto theme: Implement CSS variable–based theming using @media (prefers-color-scheme: dark) with fallback variables in main.css.
-   Frontend test coverage: Introduce React Testing Library unit tests for ChatWidget, MessageList, and ProductCard; Playwright end-to-end tests against the mock mode.
-   Rich product cards: Add product images (imageUrl field), variant selectors, and add-to-cart actions inline in the recommendation card.
